## リリース本文と配布物の自動作成

GitHub Actionsの **Meltype-flash release** を `rust` ブランチで実行し、`tag` に次の版（例: `flash-v0.1.0-preview.7`）を指定します。Cargoの版も対応する `0.1.0-pre.7` に更新しておく必要があります。比較元は既定の `auto` で現在版より前の最新タグを選びます。

Windows・Linux・macOS（Apple Silicon / Intel）・Android・ChromeOS・iOSのビルドと検証が全て成功すると、全OSの配布ファイルを添付したリリースの**下書き**を自動作成します。既存の同じタグのリリースは上書きしません。公開は下書きの内容を確認してから行います。

同じ実行のWindowsランナーで以前の版と現在版を測定し、比較条件・全ケースの表・CPUとRAMの表・箱ひげ図5枚を本文へ入れます。表と画像はGitHubのMarkdown APIで描画を検査します。測定対象はWindows上の共通Coreで、各OSの実機入力の性能を示すものではありません。

画像は `release-media` ブランチへ保存し、変更されないコミットSHAのURLを本文へ埋め込みます。画像・ベンチマークZIP・レポート・生データ・重複ZIP・単独の説明書やビルド記録はリリースのAssetsへ添付しません。処理の受け渡し用CI成果物は1日保持です。

CLIは引数なしでstdinからJSONを1行ずつ受け取ります。`{"op":"key","vk":0,"ch":107}`、`{"op":"key","vk":32,"ch":32}`、`{"op":"commit"}`、`{"op":"select","index":0}`、`{"op":"reset"}`、`{"op":"direct","enabled":true}`。再変換は `{"op":"reconvert_selection","text":"橋","reading":"はし"}`（readingは省略可）、確定Undoは `{"op":"undo_commit","before":"キャレット直前の文字列"}`。結果は `consumed/commits/view` のJSONです。削除時は `expect`、再変換開始時は `selectionExpect` をホスト側で必ず照合してください。vkは既存実装と同じWindows仮想キー、chはUnicodeスカラー、modifiersはShift=1/Ctrl=2/Alt=4/Command=8です。

## OSとの接続

Linux IBusのRust版は `bash rust/build-linux.sh` で `linux/build/Meltype-flash-linux/` と、実行権限を保持する配布用の `linux/build/Meltype-flash-linux.tar.gz` に組み立てます。ビルドには `libibus-1.0-dev` が必要で、実行時はシステムのIBus/GLibを利用します。Rust側のエンジンとOS接続は同じ実行ファイルに含まれ、Python、GI、別のRust DLLは実行時に不要です。既存のPython版は上流実装の参照用として残っています。fcitx5は引き続き既存C++アダプターです。

入力ソース用アイコンは元版の `linux/icon.png` をそのまま同梱し、登録XMLにインストール先の絶対パスを記録します。日本語・空白・引用符を含む配置先でも、アイコンの内容と登録パスをインストール試験で照合します。

生成フォルダーで `sudo bash install.sh --system` を明示的に実行すると、`/usr/libexec/meltype-rust/ibus` にプログラムを置き、IBusが通常読み込む `/usr/share/ibus/component/meltype-rust.xml` を登録します。既存の上流版の登録やRustの設定・学習データは置き換えません。IBusの再起動や入力ソースの選択は行わず、サインインし直した後に「Meltype-flash」を選びます。`sudo bash /usr/libexec/meltype-rust/ibus/install.sh --system --uninstall` は専用マーカーと登録名を確認して配布ファイルを削除し、設定・学習と未知のファイルは保持します。`--prefix` は別の絶対パスへの配置用です。登録・削除は一時フォルダーだけで検証しています。

管理者権限を使わない `bash install.sh` はユーザーのデータフォルダーへ配置します。ただしIBusはこの登録先を通常は自動で読みません。この方式ではIBus起動前に `IBUS_COMPONENT_PATH` へ表示されたフォルダーとシステムの登録フォルダーを設定する必要があります。削除は `bash install.sh --uninstall` です。

`meltype-ibus --version` は版を表示し、`--print-component` は実行ファイルの現在位置に対応するIBusのXMLを出力します。`--ibus` は登録されたIBusから起動される入口で、引数なしは検証用の動的コンポーネント登録です。どちらも通常のユーザー設定へ入力ソースを追加しません。Mozcヘルパーは `mozc/meltype_mozc_helper` または `MELTYPE_MOZC_HELPER` で指定します。ヘルパーを同梱できないビルドは内蔵補助辞書に限られ、元版の変換語彙とは同等ではありません。

`xvfb-run -a dbus-run-session -- /usr/bin/python3 rust/ibus/tests/integration.py target/release/meltype-ibus` は別のIBusデーモン・候補パネル・合成入力欄でRust実行ファイルを検証します。`MELTYPE_IBUS_TEST_INSTALLED=1` を付けると、一時フォルダーへの実インストール後にXMLからIBusが自動起動する経路で同じ10ケースを検証します。Python/GIはこのテスト用クライアントだけで使用します。フォーカスを外した場合はIBusが表示中の未確定文字を確定するため、Rustは同じ文字を再挿入せず、その表示を学習します。Enterによる確定では従来どおり末尾の `n` もかなに確定します。通常のデスクトップアプリ・Wayland/X11・サインインし直した後の動作は未検証です。

デスクトップの既存ビルド手順はそのままで、上記のRust用ビルドだけがRustエンジンを選びます。C APIは `rust/native/include/meltype.h` を参照。戻り値はmalloc由来で `meltype_free` で解放し、同一セッションの呼び出しを直列化してください。Macの変換コールバックはmalloc由来の文字列を返します。LinuxのMozcヘルパーには上流と同じC/US/RSプロトコルで接続し、応答のタイムアウトとサイズ制限を設けています。

WindowsのRustビルドは、元の `DisplayAttributes.cpp` をコンパイルせず、Rustの `ITfDisplayAttributeInfo` / `IEnumTfDisplayAttributeInfo` を使用します。入力中の点線・変換済みの細線・選択文節の太線、GUID、日本語説明とアプリの色を維持します。COM参照は `Release`、説明のBSTRは `SysFreeString` で解放します。通常の文字列用 `meltype_free` と混用しないでください。`rust/native/tests/tsf_com_smoke.py` はSDK互換のvtableを実際に呼び、Rust DLLに実装があることも照合します。CIは64bitと32bitのPythonプロセスで、TSFシェルのCOMプロバイダーからの表示属性取得まで確認します。

`LangBar.cpp` もRustビルドから除外し、入力モードボタン・`ITfSource` の通知購読・「あ／A」の描画・ツールチップ・クリックをRustで処理します。元と同じGUID・日本語表示・タスクバーの明暗に合わせた透明アイコンを使います。残るC++入力サービスにはモード取得と切替のコールバックだけを接続し、終了時に切り離します。コールバックは生成したTSFスレッドでだけ実行し、通知先が通知の途中で購読を解除する操作にも対応します。COM試験では両インターフェースの同一性、モード切替、再入する通知、終了後の切離し、アイコンの非空画素・透明度・リソース解放を確認します。現在の環境で描画した2種類のアイコンは元C++版と全画素が一致しています。

`CandidateWindow.cpp` もRustビルドから除外しました。Direct2D／DirectWriteの候補・注釈・入力キー・訂正提案・予測表示、9件のページ、選択色、画面内配置、1.5秒後の意味欄をRustで処理します。ウィンドウは入力欄のフォーカスを奪いません。文字の寸法・フォント・余白・テーマ色・色付き絵文字の描画方式を元版から移し、現在の環境では6種類の表示と意味欄の寸法・クライアント画素が元C++版と一致します。`tsf_candidate_smoke.py` は実際の非アクティブHWNDを生成し、x64/x86でページ番号の対応・予測クリック・タイマー取消・画面端の配置・複数UIスレッド・クリック中の破棄を検証します。比較用の `reference_candidates.cpp` は元ソースを直接コンパイルするテスト専用DLLで、製品には同梱しません。キー処理・編集セッション・COMサーバー登録などのTSF接続にはまだC++が残り、実際のタスクバー・各アプリ・複数モニター上での動作は未検証です。

WindowsのクラスファクトリーもRustへ移しました。Rustビルドは元のC++ `ClassFactory` を除外し、`DllGetClassObject` からRustの `IClassFactory` を返します。クラスとインターフェースの照合、非集約の生成、参照管理、`LockServer` をRustで処理し、未移植の入力サービスの生成だけをC++コールバックへ渡します。ファクトリーが存在する間と明示的なサーバーロックの間は、コールバックを持つTSF DLLを使用中として保持します。

明示的な `DllRegisterServer` / `DllUnregisterServer` もRustの登録処理へ接続しました。元と同じHKLMのCOM登録先、日本語プロファイルID・言語ID、5種類のカテゴリ、Apartment設定、シェルDLLのアイコンを使います。登録が失敗した場合のカテゴリ・プロファイル・COMの後片付けと、削除を続行する動作を代替バックエンドで検証します。実際のユーザー環境への登録・解除・有効化は行っておらず、その動作は未検証です。

編集セッションの `ITfEditSession` オブジェクト・`RequestEditSession` 呼出・即時結果と非同期結果の扱いもRustへ移しました。非同期要求ではOSが保持するCOM参照が残る間、C++側の入力編集コールバックとDLLを保持します。実行・取消・即時拒否の各経路でコールバックを一度だけ解放し、捕捉したCOM参照などを破棄してからDLLの使用中参照を解放します。`tsf_edit_session_smoke.py` は制御したITfContextを使い、x64/x86で6経路の実COM呼出を確認します。`build-edit-session-host.ps1` は実際のTSFシェルのオブジェクトファイルをテストプログラムへリンクし、捕捉したC++ラムダの寿命・DLL参照も確認します。テストは実際の入力欄やIME登録を操作しません。キー処理・未確定文字の制御・COMサーバーの薄いDLL入口は引き続きC++です。

周辺文字の前4000・後20文字の取得、確定済みの語を置き換える前のUTF-16照合、文字列の書込み・属性解除・キャレット移動もRustへ移しました。選択範囲が空でなければ前方削除を拒否し、確認用の複製と実際の範囲移動の両方で移動数を確認します。文字が読めない・期待文字列と異なる場合は書き換えません。`tsf_range_smoke.py` は制御したCOMホストのUTF-16文書で、絵文字、非空の選択、部分移動、読み書きの失敗、キャレット保持、空の確定、取得範囲とCOM参照の解放をx64/x86で検証します。

未確定入力の `StartComposition`・表示更新・終了・文節ごとの下線属性もRustへ移しました。選択範囲または明示した範囲から開始し、文節境界はUTF-16単位で設定します。文節の長さが表示文字列と一致しない場合や文字を書けない場合は、属性とキャレットを更新しません。更新と終了の間はCOM参照を保持し、ホスト側から参照が解放される通知にも対応します。C++側も終了通知で既に解放された参照を二重に解放しません。`tsf_composition_smoke.py` はx64/x86で8ケースを確認します。キー判定・フォーカス・通知の振分けはC++に残り、通常のアプリでの入力はまだ未検証です。

アプリが打ちかけの文字を確定した後の再開用状態もRustが保持します。元版と同じ1〜63 UTF-16単位の文字だけを対象に、保存した入力欄・文字列・キャレットの両端を照合し、その文字の直後で選択範囲が空の場合だけ再開します。文字は挿入し直しません。状態は成功・失敗で消費し、不要になった場合はC++側から明示的に破棄します。保持するCOM参照は作成スレッドで解放し、別スレッドからのトークン使用は拒否します。再開した未確定入力を所有者へ渡してから下線を復元するため、その最中の終了通知にも対応できます。`tsf_recovery_smoke.py` はx64/x86で各10ケースを確認します。再開対象とする通知の判定と、再開できなかった場合のコアへの確定通知は引き続きC++側です。

複数の確定・置換を順に適用するループもRustへ移しました。前の確定範囲の後ろに次の確定を続けるため、処理の途中でアプリのキャレットが移動しても挿入先を変えません。変換中の範囲外の語を訂正せず、置換前の照合や書込みが失敗した場合は残りを適用せずにコアをリセットします。既に成功した確定は文書に残します。`tsf_commit_smoke.py` はx64/x86で9ケースを確認し、`commit_batch_host.cpp` は実際のシェルのJSON受渡し・UTF-16コールバック・参照解放も試験します。通常の書込みが失敗した際の扱いなど、元版の動作は維持しています。応答の表示更新・入力中止・フォーカス・キー制御と、実アプリでの検証は引き続き残っています。

前の入力欄で確定できなかった未確定入力の保持と遅延終了もRustへ移しました。元版と同じ最大8件を保持し、Rust製の編集セッションから、その入力欄の下線を消して終了します。遅延要求は所有者・入力欄・未確定入力のCOM参照を保持し、拒否・取消でも参照を解放します。終了通知ではIUnknownの同一性で一覧から外し、無効化時は同期終了を試み、拒否された分は既存の遅延要求で処理できます。同期終了が成功した場合やアプリ側で既に終了した場合は二重に終了せず、終了失敗時は遅延要求から再試行できます。再度有効化すると、前の有効化時の要求は新しい入力を変更しません。`tsf_abandoned_smoke.py` はx64/x86で各15ケースを確認します。通常の確定・キー・フォーカスの判断とコアへの通知はまだC++側で、実アプリでの入力は未検証です。
